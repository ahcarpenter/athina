# Project agent memory

Athina: a macOS menu-bar app (Swift 6, SwiftUI, SwiftPM) that senses what the user is doing and journals it. README.md is the authoritative description of architecture, permissions, and the privacy model.

- Build, run, test: `make build`, `make run`, `make test` (see `Makefile`, `scripts/bundle.sh`). CI on `macos-26`: `ci.yml` runs `build-and-test` and `ui-snapshots-smoke` on every pull request push and push to main; `merge-checks.yml` runs `ui-snapshots`; both UI checks are split across four runners by the fixed `SnapshotShard.assignment` (a new snapshot needs a line there), and `ui-snapshots` runs on push to main and on a pull request only while it carries the `merge-checks` label (`gh pr edit <number> --add-label merge-checks`), never through a dispatch, whose checks a pull request ignores; the `main` ruleset (`.github/rulesets/main.json`) requires all three at the pull request's head before merge, and the Xcode archive check is out of CI until the App Store release flow brings it back (README "Continuous integration").
- The only Xcode project is generated, for the App Store route: `project.yml` is the spec, `make xcodeproj` generates the gitignored `Athina.xcodeproj` with the XcodeGen pinned in `Tools/XcodeGenTool`, and nothing else builds from it (README "The Xcode project"). Its target compiles `Sources/Athina` itself, so a dependency or framework added to the package's `Athina` target goes into `project.yml` too, except the `ControlAPI`-conditional `AthinaControl`, which the App Store build never carries.
- UI checks without a person at the screen: `build/Athina.app/Contents/MacOS/Athina --snapshot <dir>` renders every window to PNG (see `Sources/Athina/Snapshots.swift`) from windows parked behind the desktop, so it never shows on a shared screen; needs no permissions or API key. `open -n build/Athina.app --args --replay <dir> --open debug` (or `settings:models` or another pane, `history`) starts a replay with that window open for real screenshots (`screencapture -l <window id>`); the debug panel is otherwise reached only once Settings > Advanced > Enable debug panel (off by default) is on, from that pane and the menu's Debug Panel command, and a replay or recording opens it with `--open debug` regardless (`DebugPanelAccess`, README "Debug panel"); never drop the `--replay`, since a bare `open -n` goes round `scripts/launch.sh` and starts a second live Athina on the live journal, settings and bill. UI changes keep to README "Design conventions" (HIG choices, `StatusLabel`/`StatusBadge` for status). Waits need no real time: everything time-based reads the injected `AthinaClock` (never `Date()` or `Task.sleep`; only system measurements and UI polling stay real), tests advance an `AdjustableClock` and wait on published events, and a replay compresses minutes with `--time-scale <n>`, `--advance-clock <interval>`, the debug panel's Advance field, or `scripts/advance-clock.sh <pid> <interval>` (README "A faster clock").
- UI drift is gated in CI twice, from one list of snapshots (`Snapshots.specs()`): `ui-snapshots` renders them through the window server, glass included, against `Tests/Snapshots` (README "UI snapshot baselines"), and `ui-snapshots-smoke`, the fast check, draws them in the test process with swift-snapshot-testing against `Tests/UISnapshotsSmokeTests/__Snapshots__` (README "UI snapshot smoke test"; behind the `UISnapshotsSmoke` package trait, which only `make ui-snapshots-smoke` turns on, so plain `swift test`, `make test` and local validation never build or run it). A change that alters any snapshot, adds one or removes one fails both until approved with `make snapshots-approve` and `make snapshots-smoke-approve`, which take the images from the runner's merge-checks and CI runs of HEAD; never commit renders from a Mac, and approve only a drift the change meant. Sample data stands still at `Snapshots.referenceDate`; a view that moves on its own (a repeating effect, a ticking readout) honours `drawsStill` so renders stay identical.
- End-to-end checks against the running app go through `scripts/e2e/athina-e2e` (README "End-to-end harness"), never through hand-written driving: one warm replay home cloned per run (a cold home stalls 30 to 60 s in OCR on its first capture), named scenarios, `athina-drive` for toasts, real clicks, the accessibility tree, event taps and journal queries, and the safety a shared Mac needs (sandbox, the captain's apps excluded, the `com.ahcarpenter.athina` preferences domain saved and restored, only the pids it started stopped, one scenario on the screen at a time machine-wide on `~/Library/Caches/athina-e2e/screen.lock` and one run per checkout on `build/athina-e2e.lock`, so call it bare rather than wrapped in `lockf`, which would also hold the lock through the build it does before taking it). Its replays run with `--replay-latency immediate` (README "Replay"), so a toast comes seconds after the first capture. It needs a display, so it never runs in CI; its pure parts have unit tests that do. Scenarios are API tier (`SCENARIO_TIER=api`: driven through the app's in-app control API, `--control` and `athina-drive api`, which finds controls in Athina's own accessibility tree and clicks through its own event path, no idle waits) or real-screen tier (only what macOS routing proves: the menu bar item and its system-run menu, clicks in other apps, the item's width); give every control a scenario touches an accessibility identifier (the exceptions are system-drawn: the Settings toolbar tabs, which SwiftUI gives none, are found by label, and a window's title-bar buttons by subrole, such as `AXCloseButton`). The control API exists only under the `ControlAPI` package trait (development bundle) and in an unsandboxed replay (`ControlMode`); never add it to a release build, which `scripts/check-no-control-api.sh` refuses (README "The control API").
- Model calls cost the captain API credits, so never make a live one just to build, test, or verify: exercise the app with `make run-replay` (or `open -n build/Athina.app --args --replay <dir>`), which answers every call from recorded fixtures with no key, network, or spend, keeps its own journal and settings in a new directory per launch, which it names on the `Athina started: pid <pid> in <directory>` line a script reads rather than dictating, starts from `--settings <file>` when given so a check never swaps the live settings, and is marked Replay in the menu bar, debug panel, and journal (README "Iterating without the network"). Live calls are only for deliberate recording (`make record`), including re-recording the committed fixtures, and the separate live-quality check. Tests replay `Tests/AthinaCoreTests/Fixtures/Replay` or use `ScriptedClaudeClient`, never the network. Only `MentorLoop.perform` reaches the `ClaudeClient` seam, only to `api.anthropic.com`, only with a key the user pasted into Settings > Models (login keychain; never search for one). Prompts and schemas are versioned in `Sources/AthinaCore/Mentor/Prompts.swift`; bump the version when they change. A stale committed fixture, or a call kind with none, fails `swift test` (`make fixture-status` runs just that check), so a change that bumps the version or adds a call kind re-records the committed fixtures live in the same change: a deliberate, few-cents `make record` session on a staged scenario and an empty journal (README "The committed fixtures"). `make run-replay ALLOW_STALE=1` only replays stale fixtures locally while iterating on prompts. Model ids and prices live in `ModelCatalog.swift` with the date they were checked.
- Several Athinas share one Mac (other checkouts, lanes, the captain's own): launch targets stop only the pid their lane launched (`scripts/launch.sh`, `build/<lane>.pid`, found by a unique `--launch-token`), replays run side by side (`make run-replay LANE=<name>`), and scripts address an instance by pid, never quitting or scripting Athina by name (README "Replays side by side"). A live launch refuses while another live Athina runs, since both would share the journal, the settings, and the bill; a replay's data directory is the app's own to choose, so no launch can be pointed at the live folder or at another replay's; a lane whose journal does not open is reported as a failed launch and stopped, since it can journal nothing; and `scripts/advance-clock.sh` fails when the replay does not answer, so a clock that never moved is never reported as success.
- The app icon and the menu bar mark are generated, not hand-drawn, from two masters: `Resources/Mark/AthinaMark.svg` (the Athena drawing, app icon only) and `Resources/Mark/AthinaOwl.svg` (the owl, menu bar only), and `make mark` (`scripts/mark-assets.swift`) rebuilds both, plus the README's icon (macOS's own rendering of the new `.icns`), with the outputs committed so a plain `make build` needs nothing else. Never edit a generated asset; change a master, the script or the variant table and rerun. `make mark` records all three in `Resources/Mark/built-from.txt`, and `MarkAssetTests` fails when they fall out of step, including the rule that every variant is one width. macOS 26 masks a legacy `.icns` to the app icon shape and adds the shadow itself, so the icon art is full bleed and draws neither (README "Design conventions").
- Every gating decision is a pure function in `MentorScheduler` (`triageGate`, `mentorGate`, `refreshGate`, `publishGate` for showing a finished suggestion, `followUpGate` for a spoken question); add new gating conditions there, not in the loop or the UI. The mentorship contexts (README "Mentorship contexts") are enforced in `triageGate`, `mentorGate`, and `refreshGate` only.
- Settings editors must not bind a control straight to a field `validated()` normalizes: `AppState.settings.didSet` re-validates on every keystroke, so a name would be trimmed and an empty new row dropped mid-edit. Edit a local copy and commit it (see `ContextsSettings.swift`).
- `SuggestionCategory`'s raw values are the schema enum the model must emit, so a multi-word case needs an explicit snake_case raw value matching the prompt text. Enum names reach the model; renaming one is a prompt change.
- Journal schema changes: `migrate` uses `CREATE TABLE IF NOT EXISTS`, which never alters a table an older build created, so a new column must also go through `addColumn` (`Journal.swift`) or it is missing on every existing journal, and a removed one through `dropColumn` or an older NOT NULL column fails every insert. A new table also needs a line in `clear(at:)` and in `applyRetention`.
- Performance numbers: `make measure` while the app runs.
- Permissions: Screen Recording and Accessibility are user-granted in System Settings and cannot be granted from a shell; the app degrades to the modes listed in README.md when they are missing. Idle time needs no permission.
- Signing: no identity on the captain's machine, so `scripts/bundle.sh` signs ad-hoc with a bundle-identifier designated requirement so grants survive rebuilds; if the app reports a permission missing that System Settings shows on, the grant is bound to an old build (README.md, "Code signing"). Set `ATHINA_SIGN_IDENTITY` to override. The login keychain does not honor that requirement: the first API key read after a rebuild can show a keychain prompt only the captain can answer (Always Allow); the app reads the key off the main thread and keeps sensing behind it, but makes no live call until it is answered. A replay reads no key.
- Releasing: `make release` (README "Releasing") builds the notarized direct-download release into `build/release`; Apple credentials come only from `ATHINA_RELEASE_IDENTITY` and `ATHINA_NOTARY_PROFILE`, and without them it runs every other step ad-hoc, names what it skipped, and exits 1. The version is set only in `Resources/Info.plist`; each entitlement is justified in a comment in `Resources/Athina.entitlements`. `ATHINA_E2E_APP=build/release/Athina.app` points the e2e harness at that build, which covers the real-screen tier: the release check proves it carries no control API, so its API-tier scenarios report `skip`, and the API tier runs on the development build of the same commit.
- Callout safety lives in `CalloutAnchor` (pure, `Sources/AthinaCore/Mentor/Callout.swift`): every reason a callout is refused or taken down is a case there with a test; the overlay only draws. Callouts need Accessibility for the window frame, so screen-only mode never draws one.
- Voice: speech recognition is on-device only (`Sources/Athina/Voice`), lives in the app target, and is never touched by tests; reading suggestions aloud is deferred, not built; Microphone and Speech Recognition are optional permissions only the captain can grant. Push-to-talk uses Carbon's hotkey release event, so no Input Monitoring is ever requested. The debug panel's Talk back field sends typed words down the same path a released key does, which is how follow-ups are checked and recorded without a microphone.
- The app is Athina; the word mentor is still the vocabulary of what it does. Product names are Athina (`Athina.app`, `AthinaCore`, `AthinaClock`, `com.ahcarpenter.athina`); the strong tier, its calls, gates, loop, settings key and mentorship contexts stay mentor (`MentorLoop`, `MentorScheduler.mentorGate`, `MentorSettings`, the `mentor` key in `settings.json`, the Mentor tier label). What the model is told still says Mentor (`Prompts.swift`, `ContextBuilder`'s history line): changing it bumps the prompt version and needs a live re-record, so it moves in one deliberate change.
- Files the owner keeps move with the name, never abandoned: `DataMigration` (`Sources/AthinaCore/Settings/DataMigration.swift`) copies `~/Library/Application Support/mentor` to `athina` on the first live launch under SQLite's exclusive lock on the old journal, refuses when both hold real data (a replay's own files in `athina` are not data), stops the launch when the journal is open elsewhere or the move fails so the next launch retries, and leaves the old folder alone; `PreferencesMigration` does the same for the preferences domain, and `KeyMigration` copies the API key to the new keychain service, verifies the readback, leaves the old item, never overwrites one already there and never brings back a deleted key (its tests use in-memory stores and a throwaway domain, never the login keychain). README "Coming from Mentor".
- One binary runs sandboxed (the Xcode project's App Store target) or not, decided at runtime by `RuntimeEnvironment` from the process's own entitlement, never a compile flag (README "A sandboxed build"). Take the preferences domain and keychain service from `AppPaths`, never the literal id; a new flag or channel that names a path goes through `RuntimeEnvironment.refusal(reading:for:)`/`refusal(writing:for:)`, and tests pass an explicit environment for both answers.
- The core type is `ActivityObservation`, not `Observation`: that name collides with Apple's Observation module inside `@Observable` macro expansions.
- Never use the em dash character anywhere in this repository; use a plain dash.
